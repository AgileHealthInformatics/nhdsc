Abstract

This document specifies the requirements for Ireland's National Health Dataset Catalogue (nHDsC), the public catalogue through which health datasets subject to the European Health Data Space regulation [EHDS] are described, published and federated to the EU catalogue.

It is a proposed reference specification. It derives from HIQA's Deliverable 6.1 [D6-1], and is intended to stand on its own as a basis for procurement and acceptance testing once the policy decisions and parameters it identifies have been made.

Status of This Document

This document is a draft of a potential specification. It has no official standing of any kind and does not represent the support or consensus of any standards organization.

This is an unofficial proposal prepared as part of a consultation response. It is not a publication of HIQA, the Department of Health or any HealthData@IE partner, and has no normative standing.

The reasons for each departure from [D6-1], and the choices made in drafting this specification, are explained in the accompanying assurance report [NHDSC-ASSURANCE], supplied as a Word document.

This specification is a design proposal. None of its controls has yet been demonstrated in working software. It was prepared with substantial use of generative AI tools; the assurance report includes a transparency statement describing the approach.

Decisions that belong to the owning bodies are recorded as policy decisions in A. Policy decisions and as parameters in B. Parameters. This document is complete enough for technical consultation. It is not an implementation baseline until the policy decisions and the capacity, service-level and governance parameters are settled.

1. Conformance

As well as sections marked as non-normative, all authoring guidelines, diagrams, examples, and notes in this specification are non-normative. Everything else in this specification is normative.

The key words MAY, MUST, MUST NOT, and SHOULD in this document are to be interpreted as described in BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in all capitals, as shown here.

This specification has one conformance class. A Catalogue Service is the complete service, including its software, configuration and operating procedures, that receives, manages, publishes and federates nHDsC dataset descriptions.

An Access Management Service is the system, such as DAAMS, through which the health data access body decides on and carries out the release of data. It is subject only to the requirements in 11. Interface with access management that name it.

A Catalogue Service conforms if it meets every requirement addressed to it that uses the key word MUST or MUST NOT, as resolved by the policy decisions in force and with every parameter set. Where a requirement depends on a policy decision, it states which.

Each requirement names a verification method: test (an executable acceptance test), inspection (examination of design, data or configuration), or review (assessment by a named accountable party).

2. Introduction

This section is non-normative.

Article 77 of [EHDS] requires each health data access body to provide a publicly available, standardised, machine-readable catalogue of the datasets available for secondary use. Each description includes the source, scope, main characteristics and nature of the data, and the conditions for making it available. Most categories of data in Article 51 must be discoverable by 26 March 2029; some, including human genetic data, by 26 March 2031. The national catalogue is federated to the EU catalogue under Article 79.

Applications for access are handled by a separate Data Access Application Management System (DAAMS) and are out of scope, except for the hand-off in DS-09.

2.1 Design principles

  1. Public by default. Anything published can be found and read by anyone, without an account.
  2. One authoritative source. Each piece of information has one owner and one place where it is maintained.
  3. Reference European standards by release. The metadata schema is defined by [REG-2026-2098] and [HEALTHDCAT-AP], and is cited rather than restated.
  4. Decide first, then propagate. A decision is recorded once, durably, and then carried to every other system in a way that can be retried and checked.
  5. Separate deciding from operating. The people who decide what is published are not the people who run the systems.
  6. Every requirement is testable.

3. Terminology

Dataset
A structured collection of electronic health data held by one data holder organisation. It persists across every change to its description and every refresh of its content.
Record version
One version of the catalogue description of a Dataset. It has content (the description itself) and a workflow state, which are governed separately.
Content hash
A cryptographic digest of a Record version's content in a canonical form, used to prove that the content approved is the content published.
Data release
An identified state of a Dataset's content, such as an annual extract or a registry snapshot.
Distribution
A specific available form of a Data release, in the sense of [VOCAB-DCAT-3].
Offered release
A Data release for which a Record version lists at least one Distribution as available through the health data access body.
Quality label
A data quality and utility label under Article 78 of [EHDS], assessing one Data release.
Specification release
A pinned release of [HEALTHDCAT-AP], with its validation shapes and controlled vocabularies, that satisfies [REG-2026-2098].
Public representation
The RDF and web view of a Record version as actually published, after any authorised withholding.
Label status
The state of quality labelling for one offered release of a Dataset that requires a label: Missing (no assessment registered), Pending (an assessment is registered but not yet verified), Verified, Expired or Revoked.
Current-version pointer
The single record, held in the workflow store for each Dataset, of which Record version is public.
Staged
Held in the catalogue store but not exposed to the public.
Catalogue store
The component that holds and serves published metadata to the public. In the reference architecture this is piveau Hub.
Workflow store
The component that holds the authoritative record of lifecycle decisions, guards, labels, obligations and outbox events.
Data holder organisation
The legal entity that holds a Dataset and is accountable for the accuracy of its description.
Holder editor
A person authorised by a data holder organisation to draft descriptions.
Holder approver
A person authorised by a data holder organisation to attest to the accuracy of descriptions and submit them.
Publication authority
The function, within the health data access body, accountable for deciding what appears in the public catalogue and for verifying quality labels.
Service operator
The function that runs the infrastructure and manages platform accounts. It has no authority over catalogue content.
Registered user
Anyone who has created an account to use personal features such as saved searches and alerts.
Audit event
An append-only, integrity-protected record of a decision, state change or privileged action.

5. Information model

5.1 Identity

IM-01Each Dataset MUST be identified by an HTTP IRI that is globally unique and persistent, assigned when its first Record version is created.

Source: [VOCAB-DCAT-3] · Verify: test

IM-02A Dataset IRI MUST NOT encode the holder organisation, a version, or any other attribute that can change.

Source: persistence · Verify: test (transfer a Dataset between organisations; IRI unchanged)

IM-11Each Dataset MUST carry a dct:identifier value as required by the Specification release. The value MUST NOT change once assigned. It MAY be the IRI in literal form or an existing identifier from the holder's own systems.

Source: [HEALTHDCAT-AP] · Verify: test

IM-04Each Record version MUST have its own persistent IRI and MUST be linked to its Dataset and to its predecessor by explicit RDF relationships, as set out in the national identifier and versioning policy (GV-05).

Source: traceability · Verify: inspection

IM-12Dataset and Record version IRIs SHOULD resolve to a human-readable page and to the RDF representation, by content negotiation.

Source: linked data practice · Verify: test

Note

A simple convention, such as the Dataset IRI followed by /v and a sequence number, satisfies IM-04 and is suggested as a starting point for the policy required by GV-05.

5.2 Content and workflow state

IM-03The content of a Record version MAY be edited only while the version is in the Draft state.

Source: integrity · Verify: test (attempt to edit in every other state by API; refused)

IM-09The Catalogue Service MUST compute and record a content hash of the Record version at each complete, submit and approve transition.

Source: integrity · Verify: test

IM-10Once a Record version has been approved, its content MUST NOT change. Any later change to a description MUST create a new Record version with the next sequence number.

Source: integrity · Verify: test

IM-13Changes to workflow state MUST be recorded as audit events and MUST NOT alter the version's content or content hash.

Source: integrity · Verify: test

5.3 Version history

IM-05Holder users and the Publication authority MUST be able to see the full version history of a Dataset they are permitted to view, with each version's author, date, change reason and state.

Source: transparency · Verify: test

IM-08Any user MUST be able to compare any two versions they are permitted to view, side by side, with differences highlighted.

Source: transparency · Verify: test

The public view of version history is defined in DS-11.

5.4 Holder obligations

IM-06The Catalogue Service MUST maintain, for each data holder organisation, a register of the Article 51 categories it is obliged to describe and the date by which each must be discoverable.

Source: [EHDS] Art. 51, Art. 105 · Verify: inspection

IM-07Each obligation MUST be linked to the Dataset or Datasets that meet it, or marked as unmet. The Publication authority MUST be able to report coverage by holder and category.

Source: BR-06 · Verify: test

8. Quality and utility labels

Policy decision PD-01: when a mandatory label must exist. Article 78 of [EHDS] makes a label mandatory for certain datasets. It does not say expressly whether the label must exist before the dataset can be listed in the catalogue. This is a national policy choice, and legal advice should be taken.

Option A, strict: a dataset needing a label cannot be published until a verified label exists for every offered release.

Option B, proposed default: a dataset may be published with its label shown as "pending". Release of the data through the health data access body is withheld until a verified label exists. A label may remain pending for at most P-15 days, after which the Publication authority must act under QL-12.

Option B MUST NOT be adopted unless requirements DI-02 to DI-04 are contractual obligations of the Access Management Service, because under Option B it is the Access Management Service, not the catalogue, that stops data being released.

Option B is proposed because the catalogue's first purpose is to make datasets discoverable, and Option A would keep a dataset out of view whenever an assessment is delayed. The requirements below apply under either option; QL-10 and QL-11 state where they differ.

QL-01The Publication authority MUST determine, for each Dataset, whether a quality label is mandatory, and record the basis for the determination.

Source: [EHDS] Art. 78 · Verify: test

QL-02A quality label MUST identify the Data release it assesses, the assessor, the method, the assessment date and a review-by date.

Source: [EHDS] Art. 78 · Verify: test

QL-03Supporting evidence for each element of a label MUST be stored with the label.

Source: provenance · Verify: test

QL-13Where scores come from an assessment tool, the tool's output MUST be stored with the label, and scores SHOULD be imported from it rather than retyped.

Source: provenance · Verify: test

QL-15Each offered release of a Dataset that requires a label MUST have exactly one label status: Missing, Pending, Verified, Expired or Revoked.

Source: consistency · Verify: inspection

QL-04When a Data release that requires a label is first offered, its label status MUST be Missing, and the Catalogue Service MUST notify the holder approver.

Source: currency · Verify: test

QL-14A holder approver MAY register a pending assessment for a release, naming the assessor and the expected completion date. The release's label status then becomes Pending until a label is verified or the pending assessment is withdrawn.

Source: PD-01 · Verify: test

QL-05The Publication authority MUST verify each label before G3 can rely on it, and MAY revoke a label with a recorded justification.

Source: [EHDS] Art. 78 · Verify: test

QL-06Revocation of a label for an offered release MUST open a compliance review of every published version that offers that release, and the outcome MUST be recorded.

Source: [EHDS] Art. 78 · Verify: test

QL-07The public catalogue MUST show, for each offered release of a Dataset that requires a label, one of these label statuses: Verified, Pending, Expired or Revoked, with the assessment date where there is one.

Source: transparency · Verify: test

QL-08The catalogue MUST use distinct wording for three claims: that a description is valid, that the data has an assessed quality, and that the data suits a particular purpose.

Source: accuracy of claims · Verify: inspection

QL-10Guard G2 MUST be evaluated for every offered release separately. Under PD-01 Option A, the label status of every offered release needing a label MUST be Verified. Under Option B, it MUST be Verified or Pending. A status of Missing, Expired or Revoked MUST fail G2 under either option.

Source: [EHDS] Art. 78; PD-01 · Verify: test (a version offering a labelled older release and an unlabelled newer release; G2 must evaluate the newer release)

QL-11The Catalogue Service MUST make each offered release's label status available to the Access Management Service through the interface in DI-01.

Source: PD-01 · Verify: test

QL-12A release whose label status remains Pending for longer than P-15 days MUST be escalated to the Publication authority, who MUST record a decision to extend, revoke the version, or withdraw the release from the offer.

Source: PD-01 · Verify: test

Issue 1: Label structure

The internal structure of a label is defined by the implementing act under Article 78(6) of [EHDS]. Any tool-based scoring, such as QUANTUM, must map to it. The mapping must be agreed before build (PD-03).

11. Interface with access management

The catalogue describes data; the Access Management Service releases it. Where release depends on catalogue information, the catalogue supplies the evidence and the Access Management Service enforces the rule.

DI-01The Catalogue Service MUST provide an authenticated interface that returns, for any Dataset and Data release, the current label status, the identity and review-by date of any verified label, and the content hash of the Published version that offers the release.

Source: PD-01; [EHDS] Art. 78 · Verify: test

DI-02The Access Management Service MUST obtain the label status from DI-01 at the time of each data release decision, and MUST NOT release data from a release whose label is required and whose status is not Verified.

Applies to: Access Management Service · Source: PD-01 · Verify: test

DI-03The Access Management Service MUST record the label status it evaluated as part of each data release decision.

Applies to: Access Management Service · Source: accountability · Verify: inspection

DI-04Every route by which the health data access body can release data MUST apply DI-02.

Applies to: Access Management Service · Source: PD-01 · Verify: review

Note

DS-09, the hand-off of a user's selection to DAAMS, remains a deferred convenience. The safeguard against releasing unlabelled data rests on DI-01 to DI-04, not on DS-09.

13. Publication

Publication follows the principle "decide first, then propagate". The approval decision is committed first. The approved content is then staged in the catalogue store, out of public view, by a task that can be safely repeated. When staging is confirmed, one commit makes the version Published, moves the current-version pointer, supersedes the previous version, and releases the follow-up tasks. A further repeatable task then exposes the new version to the public. At no point does the catalogue store decide for itself which version is public.

PB-01The approval decision, the content hash and the staging task MUST be committed in a single transaction in the workflow store, as the result of the approve transition and before any write to the catalogue store.

Source: principle 4 · Verify: test

PB-06Staging and exposure in the catalogue store MUST each be idempotent: repeating either for the same version and content hash MUST have the same effect as doing it once.

Source: reliability · Verify: test

PB-17For each Dataset, the workflow store MUST hold a single current-version pointer. It is the only authority for which version is public. Moving it MUST happen in the same commit that makes the new version Published and the previous version Superseded.

Source: BR-02 · Verify: test

PB-07The catalogue store MUST NOT expose any version to the public other than the one named by the current-version pointer, subject only to the transition allowance in LC-03. Staged versions MUST NOT appear in public web pages, search results, RDF exports or query interfaces.

Source: BR-02 · Verify: test

PB-08A version MUST become Published only after the catalogue store has confirmed that the approved content hash is staged. The confirmation MUST be recorded.

Source: definition of visibility · Verify: test

PB-18Notification and federation tasks for a version MUST NOT become eligible to run until the version is Published.

Source: principle 4 · Verify: test

PB-19If exposure of the version named by the current-version pointer has not been confirmed within P-23, the Catalogue Service MUST alert the Service operator and the Publication authority.

Source: LC-03 · Verify: test

PB-09If staging has not been confirmed within P-16 after approval, the Catalogue Service MUST alert the Service operator and the Publication authority.

Source: reliability · Verify: test

PB-10A reconciliation process MUST compare the workflow store and the catalogue store at least every P-17. It MUST repair any difference automatically where the workflow store's record is unambiguous, and MUST report every difference and repair.

Source: reliability · Verify: test

PB-11Withdrawal and revocation MUST follow the same pattern: the decision and the change to the current-version pointer are committed first, and exposure follows. The public catalogue MUST stop showing a withdrawn or revoked version within P-18 of the decision.

Source: [EHDS] Art. 77(1) · Verify: test

PB-12Notifications MUST NOT form part of any state-change transaction. A failed notification MUST be retried and MUST NOT change the state of any version.

Source: reliability · Verify: test

Source: [EHDS] Art. 79 · Verify: test

PB-13Each Record version MUST have a federation status of Not sent, Pending, Accepted, Rejected or Failed, with the time of each change.

Three example tests follow. They are informative.

Feature: Staged content is never exposed early (PB-01, PB-07, PB-08, PB-17, LC-03, VT-04)

  Scenario: Confirmation of staging is lost
    Given version 3 of a dataset is Approved and version 2 is Published
    And the catalogue store stages version 3 and confirms
    And the workflow store fails before recording the confirmation
    Then the public pages, search results, RDF export and query interface show version 2 only
    When the outbox worker retries staging of version 3
    Then the catalogue store reports version 3 already staged with the same hash
    And in one commit version 3 becomes Published, the pointer moves and version 2 becomes Superseded
    And within P-23 the public interfaces show version 3 only
    And notifications for version 3 are sent only after it is Published

Feature: Labels are checked for each offered release (QL-10, G2, G3)

  Scenario: Older release labelled, newer release not
    Given PD-01 is Option A
    And a dataset requires a label
    And version 4 offers release 2024 with status Verified
    And version 4 offers release 2025 with status Missing
    When the Publication authority approves version 4
    Then approval is refused with failed guard "G2" for release 2025

Feature: Option B publishes but does not release (PD-01, QL-14, G3, DI-02, VT-05)

  Scenario: Pending label
    Given PD-01 is Option B
    And a dataset requires a label
    And a pending assessment is registered for release 2025, 10 days ago
    And version 4 offers release 2025
    When the Publication authority approves version 4
    Then guards G2 and G3 pass and version 4 is Approved
    And after go live the public catalogue shows release 2025 with label status Pending
    When the Access Management Service decides a request to release data from release 2025
    Then it obtains status Pending from the catalogue interface
    And it refuses release, recording the status it evaluated
